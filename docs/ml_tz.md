# ТЗ ML: прогноз пассажиропотока метро

ML-часть прогнозирует входы на каждую станцию на 15–120 минут вперёд с интервалом неопределённости и отдаёт прогноз в симулятор и систему рекомендаций. Методы отрабатываем на реальных данных линии 7 метро Нью-Йорка (MTA, 2023–2024), затем тот же код переносим на синтетику 1 линии Петербурга.

**Итог работы:** обученная модель с квантилями 0,1 / 0,5 / 0,9, честный бэктест против бейзлайнов, сравнение 2–3 версий модели и прогнозы в формате общего контракта.

## 1. Цель и место в системе

ML отвечает на один вопрос: сколько людей войдёт на станцию в ближайшие 15–120 минут и насколько это отличается от нормы. Решение о составах принимает не модель, а система рекомендаций человека 4 — ML даёт ей прогноз и неопределённость.

| Кто | Что даёт ML / получает ML |
| --- | --- |
| Человек 1 → ML | Погода, праздники, события в структурированном виде с меткой времени |
| ML → человек 3 | Прогноз входов по станциям для модели загрузки перегонов и симулятора |
| ML → человек 4 | Квантили прогноза и флаг аномалии для рекомендаций; от него — цена ошибки (недооценка против переоценки) |

**Контракт выхода** — договариваемся в первый день, дальше все работают на заглушках этого формата:

```json
{
  "station_id": "vosstaniya",
  "ts": "2026-11-14T18:00:00+03:00",
  "horizon_min": 30,
  "q10": 2100, "q50": 2600, "q90": 3150,
  "baseline": 1850,
  "is_anomaly": true,
  "model_version": "lgbm_events_v1"
}
```

`ts` — начало прогнозируемого слота в локальном времени со смещением; `baseline` — «расчётный» поток для этого слота и типа дня; `horizon_min` — за сколько минут до слота сделан прогноз.

### MTA: как скачать линию 7

Датасет большой — около 110 млн строк и 12 столбцов: `transit_timestamp`, `station_complex_id`, `station_complex`, `payment_method`, `fare_class_category`, `ridership`, `transfers`, координаты ([схема](https://baselight.app/u/usgov/dataset/state_of_new_york_mta_subway_hourly_ridership_beginnin_0a524e96)). Целиком не качаем: фильтруем и агрегируем на стороне сервера через SoQL API портала.

1. Получить список станционных комплексов с их ID.
2. Отобрать комплексы линии 7 по названию: в нём в скобках перечислены линии, например `Flushing-Main St (7)`. Проверить список по схеме линии — от Flushing-Main St до 34 St-Hudson Yards.
3. Скачать по этим ID сумму `ridership` по часу и станции — типы оплаты сразу схлопываются в одно число.

```python
import requests, pandas as pd

BASE = "https://data.ny.gov/resource/wujg-7c2s.json"
HEAD = {}  # при троттлинге: {"X-App-Token": "<бесплатный токен data.ny.gov>"}

def soql(params, page=50_000):
    rows, offset = [], 0
    while True:
        r = requests.get(BASE, params={**params, "$limit": page, "$offset": offset}, headers=HEAD, timeout=120)
        r.raise_for_status()
        batch = r.json()
        rows += batch
        if len(batch) < page:
            return pd.DataFrame(rows)
        offset += page

# 1–2. Комплексы линии 7
cx = soql({"$select": "station_complex_id, station_complex",
           "$group": "station_complex_id, station_complex"})
line7 = cx[cx.station_complex.str.contains(r"[(,]\s*7\s*[,)]", regex=True)]
ids = ", ".join(f"'{i}'" for i in line7.station_complex_id)

# 3. Почасовые входы, сумма по типам оплаты
df = soql({
    "$select": "transit_timestamp, station_complex_id, sum(ridership) as entries",
    "$where": f"station_complex_id in ({ids}) AND transit_timestamp between '2023-01-01T00:00:00' AND '2024-12-31T23:00:00'",
    "$group": "transit_timestamp, station_complex_id",
    "$order": "transit_timestamp, station_complex_id"})
df.to_parquet("data/raw/mta_line7_2023_2024.parquet")
```

Ожидаемый объём: около двух десятков комплексов × \~17,5 тыс. часов ≈ 400 тыс. строк — обычный pandas справляется. Набор 2020–2024 фактически начинается с февраля 2022 года; 2022-й не берём — пассажиропоток ещё восстанавливался после ковида.

## 3. Подготовка данных

Четыре папки с parquet-файлами и одно правило времени — больше инфраструктуры не нужно. Объёмы — сотни тысяч строк, Polars и ускоренный pandas не понадобятся.

| Слой | Что лежит | Кто пишет |
| --- | --- | --- |
| `data/raw/` | Выгрузки как есть: MTA, погода, события, Ханчжоу | Скрипты загрузки, без правок руками |
| `data/interim/` | Единый формат `station_id, ts, entries` + внешние таблицы, очищенные и выровненные по времени | Скрипт очистки |
| `data/features/` | Обучающая таблица: строка = (станция, момент прогноза, горизонт) | Генератор признаков |
| `data/predictions/` | Прогнозы в формате контракта, по версии модели | Модель |

**Правило времени.** Все стыковки таблиц — по `ts_utc`. Календарные признаки (час, день недели) считаются из локального времени. Причина — переход на летнее время в Нью-Йорке: в марте один час пропадает, в ноябре повторяется, и стыковка по локальному времени молча испортит эти дни. В Петербурге перехода нет, но правило то же — код одинаковый.

**Очистка:**

- **Полная сетка.** Достроить все пары «станция × час». Пропуск ≠ ноль: отсутствие строки — пробел в данных, ноль — реально закрытая станция. Помечаем отдельным флагом.
- **Выбросы и сбои.** Закрытия станций на ремонт и всплески из-за сбоев учёта найти глазами на EDA и пометить флагом, а не удалять: модель не должна на них учиться, но в данных они остаются.
- **Ночь.** Ночные часы с почти нулевым потоком оставляем, но метрики считаем по часам работы (раздел 7) — иначе они искусственно улучшают MAPE-подобные метрики.
- **Разбивка по оплате.** Уже схлопнута при скачивании; при желании добавить в запрос `sum(transfers)` — пригодится как признак пересадочного потока.

## 4. EDA: что посмотреть до моделей

Цель EDA — понять, какие эффекты в данных есть и насколько они сильны; из этого вырастают признаки. Каждый пункт — график в ноутбуке и одна строка вывода под ним.

- [ ] Суточный профиль по станциям в будни и выходные: два пика или один, где утренний пик сильнее вечернего
- [ ] Недельная сезонность: насколько похожи одинаковые часы соседних недель (корреляция с лагом 168 ч)
- [ ] Годовой тренд и сезонность: лето, декабрь, начало учебного года
- [ ] Праздники и предпраздничные дни: насколько и как меняется профиль
- [ ] Погода: поток в часы с дождём или снегом против таких же часов без осадков, по станциям
- [ ] Матчи: поток на станции у стадиона и соседних станциях до и после игры; насколько сдвинут пик относительно окончания
- [ ] Шум: разброс одинаковых слотов — какой процент отклонения считать «нормальным»
- [ ] Сбои и закрытия: дни с аномально низким потоком и их причина
- [ ] Ханчжоу: те же профили на 15-минутном шаге — сравнить форму с MTA

Главный вывод EDA для защиты: «вот как выглядит аномальный день и насколько он отличается от нормы» — 2–3 графика пойдут прямо в презентацию.

## 5. Признаки и постановка прогноза

Признаки — основная работа и основной источник качества; модель вторична. Постановка — прямой многошаговый прогноз одной глобальной моделью.

**Постановка.** Строка обучающей таблицы = (станция, момент прогноза t, горизонт h), цель — входы в слоте t + h. Горизонт — обычный признак. На MTA с часовым шагом h = 1 и 2 часа; на 15-минутной синтетике СПб h = 1…8 шагов (15–120 минут). Одна модель на все станции и горизонты: данных больше, станции «учатся» друг у друга.

Почему не рекурсивно (прогноз на шаг, потом подставить его как лаг): ошибки накапливаются, а внешние признаки на горизонте h всё равно приходится подавать отдельно. Прямая схема проще и честнее.

**Правило против утечек:** признак строки должен быть известен в момент t. Лаги считаются от t, а не от t + h; погода на t + h — из прогноза, сделанного до t; событие — только если о нём было известно заранее.

| Группа | Признаки | Комментарий |
| --- | --- | --- |
| Лаги потока | Входы в t, t−1, t−2, t−3 шага; тот же слот, что t + h, вчера и неделю назад | Слот «неделю назад» берётся для целевого времени t + h — это сильнейший признак |
| Окна | Среднее и стандартное отклонение за последние 3 и 24 шага; отношение текущего потока к бейзлайну | Текущее отклонение от нормы — главный сигнал аномального дня |
| Бейзлайн | Медиана потока для (станция, слот, тип дня) за последние 4–8 недель | Тот же «расчётный поток», что уходит в контракт |
| Календарь | Час, слот, день недели, тип дня, праздник, предпраздничный и послепраздничный день, месяц | Час и день недели — категории или sin/cos |
| Погода | Температура, осадки, снег, ветер на t + h; осадки за последние 3 ч; «резкое ухудшение» | Для обучения — исторические прогнозы Open-Meteo |
| События | Есть ли событие у станции; минуты до начала и после окончания; вместимость площадки | От человека 1 — признаками, а не готовым «числом людей» |
| Станция | ID (категория), годовой объём, тип: конечная / пересадочная / у стадиона | Позволяет переносить модель на новые станции |

Для генерации лагов и окон удобна библиотека `mlforecast` (Nixtla): она строит признаки и бэктест по нескольким рядам сразу. Но схему «тот же слот для t + h» и внешние признаки на t + h проще собрать вручную в pandas — так её легче проверять на утечки.

## 6. Модели

Основная модель — LightGBM с квантильной функцией потерь; всё остальное — бейзлайны для сравнения или запасные варианты. Идём по лестнице снизу вверх и переходим на следующую ступень, только когда предыдущая честно измерена.

| Ступень | Модель | Зачем |
| --- | --- | --- |
| 0 | Сезонный наивный: тот же слот неделю назад | Нижняя планка; любая модель обязана её бить |
| 1 | Профильный бейзлайн: медиана (станция, слот, тип дня) за 4–8 недель | «Расчётный поток» из задания; против него меряем пользу ML |
| 2 | Бейзлайн × текущее отклонение (поправка на то, насколько сегодня выше нормы) | Простой и сильный вариант для коротких горизонтов; запасной для демо |
| 3 | **LightGBM, квантили 0,1 / 0,5 / 0,9** — без внешних признаков | Основная модель, версия «только история» |
| 4 | LightGBM + погода + события | Главная версия; разница с ступенью 3 — польза внешних факторов |
| 5 (опц.) | CatBoost `MultiQuantile` | Проверка, что результат не артефакт одной библиотеки; удобные категории |

**Почему бустинг, а не нейросети.** Табличные признаки, сотни тысяч строк, нужен результат за дни и объяснимость через важность признаков. Нейросетевые модели рядов (N-HiTS, TFT) на таком объёме редко выигрывают у хорошо собранного бустинга, а времени съедают в разы больше. Если останется время — можно попробовать одну через `neuralforecast` для слайда «мы проверили».

**Как учить квантили:**

- Три модели LightGBM с `objective="quantile"` и `alpha` = 0,1, 0,5, 0,9.
- Цель — `log1p(entries)`: ряд становится ровнее, а квантили при монотонном преобразовании переводятся обратно точно через `expm1`.
- Квантили изредка «перекрещиваются» (q10 > q50) — после предсказания сортируем три значения в каждой строке.
- Стартовые параметры: `learning_rate` 0,05, `num_leaves` 63, `min_data_in_leaf` 100, `feature_fraction` 0,8, ранняя остановка по валидационному фолду. Тюнинг — в последнюю очередь и немного: признаки дадут больше.

```python
import lightgbm as lgb, numpy as np

models = {}
for a in (0.1, 0.5, 0.9):
    m = lgb.LGBMRegressor(objective="quantile", alpha=a, learning_rate=0.05,
                          num_leaves=63, min_child_samples=100, colsample_bytree=0.8,
                          n_estimators=3000)
    m.fit(X_tr, np.log1p(y_tr), eval_set=[(X_va, np.log1p(y_va))],
          callbacks=[lgb.early_stopping(100, verbose=False)], categorical_feature=cat_cols)
    models[a] = m

pred = np.column_stack([np.expm1(models[a].predict(X_te)) for a in (0.1, 0.5, 0.9)])
pred.sort(axis=1)  # q10 ≤ q50 ≤ q90
```

**Какой квантиль отдавать в рекомендации.** Все три идут в контракт. Решение «выпускать резерв» человек 4 принимает по верхнему квантилю. Если его оценка цены ошибки скажет, что недооценка дороже переоценки, например, в 4 раза, оптимальный уровень — 4 / (4 + 1) = 0,8: тогда добавляем модель с `alpha` = 0,8. Это и есть связь ML с экономикой.

## 7. Валидация и метрики

Проверяем только «из прошлого в будущее»: обучаемся до даты, прогнозируем следующий отрезок, сдвигаемся. Случайное перемешивание строк запрещено — оно даёт модели подсмотреть будущее и завышает качество.

&#91;embedded content: Схема бэктеста · 6 фолдов и финальный тест\]

**Схема.** Первое обучение — весь 2023 год. Дальше 2024 год режется на 6 тестовых блоков по 2 месяца; перед каждым блоком модель дообучается на всём, что было раньше (расширяющееся окно). Между концом обучения и началом теста — зазор в неделю, чтобы недельные лаги не заглядывали в тест. Финальная проверка — один раз, в конце, на первом квартале 2025 года, который до этого не трогаем вообще.

**Метрики** — считаем по часам работы метро, отдельно по каждому горизонту и отдельно для аномальных дней:

| Метрика | Что показывает | Ориентир |
| --- | --- | --- |
| WAPE = Σ\|факт − прогноз\| / Σ факт | Средняя относительная ошибка, устойчива к малым значениям | Ниже, чем у бейзлайна ступени 1 |
| MAE по станциям | Ошибка в людях — понятна диспетчеру и человеку 4 | Для слайда |
| Pinball loss по квантилям | Качество квантилей в целом | Ниже, чем у бейзлайна |
| Покрытие интервала q10–q90 | Доля фактов внутри интервала | ≈ 80% |
| Recall и precision аномальных слотов | Ловит ли модель «необычные» часы | Recall важнее: пропуск толпы хуже ложной тревоги |
| Время упреждения | За сколько до превышения порога пришёл сигнал | ≥ 30–60 минут — время выпустить резерв |

**Абляции — таблица для защиты.** Заполняем по мере готовности; каждая строка отвечает на вопрос «что дала эта часть»:

| Модель | WAPE, все дни | WAPE, аномальные дни | Покрытие q10–q90 |

| Профильный бейзлайн |  |  |  |
| LightGBM, только история |  |  |  |

Конечная оценка — не WAPE, а экономика после симулятора и рекомендаций (задача человека 4): 2–3 лучшие версии прогоняем через всю цепочку и сравниваем стоимость работы линии при тех же ограничениях.

## 8. Аномалии и перенос на 1 линию СПб

### Флаг аномалии

Слот помечается аномальным, если прогноз q50 выходит за 90-й перцентиль исторических значений этого слота (станция × слот × тип дня) или опускается ниже 10-го — и так два слота подряд. Два подряд — защита от единичного шума. Пороги подбираем на бэктесте под нужный баланс recall и precision.

Для проверки нужна разметка: на MTA аномальные дни размечаем сами по EDA (праздники, снегопады, матчи, сбои), на синтетике разметка есть сразу — мы сами закладываем эффекты.

### Генератор синтетики для 1 линии

Реальных 15-минутных данных Петербурга нет, поэтому демо работает на калиброванной симуляции. Генератор — тоже ML-задача: только ты знаешь, какие эффекты модель должна уметь ловить.

**Входы (станция s, слот t) = V\_s × p\_тип дня(t) × ∏ e\_k(s, t) × ε(s, t)**

V\_s — дневной объём станции s (годовой объём из отчёта комитета, делённый на число дней с поправкой на тип дня); p(t) — доля дня в 15-минутном слоте, форма суточного профиля из Ханчжоу или MTA с поправкой на конечные и центр; e\_k — множители эффектов: снег, дождь, вокзалы (по расписанию поездов), события, праздники; ε — шум с разбросом, измеренным на EDA.

Каждый эффект пишется в отдельный столбец-разметку. Тогда проверка «модель поняла снегопад» становится измеримой: смотрим ошибку именно в слотах со снегом.

### Что переносится, а что нет

- **Переносится без изменений:** код очистки, генерации признаков, обучения, бэктеста и выдачи по контракту. Меняется только источник данных и шаг (час → 15 минут).
- **Переобучается:** сама модель — на синтетике СПб. Модель, обученная на Нью-Йорке, напрямую к Петербургу не применяется.
- **Подаётся честно:** метрики на синтетике не выдаём за реальные. На защите: «методы проверены на реальных данных MTA и Ханчжоу, демо работает на калиброванной симуляции 1 линии; при реальных данных турникетов меняется только источник».
